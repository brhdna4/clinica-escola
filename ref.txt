============================================================

8. MÁQUINA DE ESTADOS DO ATENDIMENTO
============================================================

Status principais:
- Solicitado
- Confirmado
- Em Atendimento
- Finalizado
- Saiu

Representação técnica sugerida:
REQUESTED | CONFIRMED | IN_PROGRESS | FINISHED | CHECKED_OUT

Transições válidas padrão:
REQUESTED → CONFIRMED
CONFIRMED → IN_PROGRESS
IN_PROGRESS → FINISHED
FINISHED → CHECKED_OUT

Transições inválidas devem ser bloqueadas.
Exemplos de transições que devem ser negadas, salvo regra especial já existente:
REQUESTED → IN_PROGRESS
REQUESTED → FINISHED
REQUESTED → CHECKED_OUT
CONFIRMED → FINISHED
CONFIRMED → CHECKED_OUT
IN_PROGRESS → REQUESTED
FINISHED → REQUESTED
CHECKED_OUT → qualquer status anterior

Regras:
1. Toda transição deve validar permissão do usuário.
2. Toda transição deve validar o status atual.
3. Toda transição deve atualizar updatedAt.
4. Toda transição deve incrementar version, se existir controle de concorrência.
5. Toda transição deve propagar evento para Index/Panel.
6. Se a transição falhar, manter estado anterior.
7. Se houver status adicionais no código, mapeá-los e validá-los sem criar UI nova.

Eventos de domínio sugeridos:
- appointment.requested
- appointment.confirmed
- appointment.started
- appointment.finished
- appointment.checked_out
- appointment.updated
- availability.blocked
- availability.unblocked
- patient.created
- patient.matched

Esses eventos são apenas lógicos. Não exigem UI nova.

9. REGRAS DE NEGÓCIO CRÍTICAS
============================================================

9.1 Disponibilidade
Ao calcular horários disponíveis, considerar:
- sala/consultório ativo;
- sala não bloqueada;
- profissional/aluno ativo;
- profissional/aluno disponível;
- ausência de agendamento conflitante;
- capacidade/lotação da sala;
- data/hora futura;
- duração válida;
- regras de bloqueio existentes.

9.2 Conflito de horário
Não permitir dois agendamentos simultâneos quando houver interseção de:
- mesma sala;
- mesmo profissional/aluno;
- mesmo paciente.

Fórmula de conflito temporal:
startA < endB AND startB < endA

9.3 Paciente novo
- Validar campos obrigatórios existentes.
- Evitar duplicidade segundo critérios existentes.
- Criar paciente antes ou junto com agendamento, de forma atômica.
- Se falhar, não deixar estado parcial inconsistente.

9.4 Paciente antigo
- Buscar paciente por mecanismo existente.
- Não duplicar cadastro.
- Vincular novo agendamento ao paciente existente.
- Se busca retornar múltiplos resultados, usar seleção existente.
- Se não houver mecanismo de desempate, reportar como risco sem criar UI nova.

9.5 Sala/consultório
- Sala bloqueada impede novos agendamentos.
- Sala lotada impede novos agendamentos.
- Sala inativa impede novos agendamentos.
- Se houver agendamento futuro para sala bloqueada, tratar conflito sem apagar silenciosamente.

9.6 Aluno/profissional
- Aluno/profissional inativo impede novos agendamentos.
- Aluno/profissional ausente/bloqueado impede novos agendamentos.
- Se houver agendamento futuro vinculado a aluno bloqueado, sinalizar inconsistência lógica.

9.7 Recepção/fluxo
- Recepção deve conseguir operar entrada/saída conforme estados válidos.
- Taxa de utilização, se existir, deve ser calculada com base em dados consistentes.
- Não alterar visualmente indicadores existentes.

9.8 Chat, se existir
- Validar usuário logado.
- Validar permissão de leitura/escrita.
- Não permitir mensagens órfãs sem autor.
- Não criar novo chat se não existir.

11. PERSISTÊNCIA E ARMAZENAMENTO
============================================================

Cenário A — Sistema usa localStorage/sessionStorage:
- Usar chaves estáveis.
- Não quebrar dados já salvos.
- Criar migração defensiva se houver mudança de schema.
- Validar JSON antes de parsear.
- Tratar payload corrompido.
- Evitar sobrescrita concorrente.
- Escutar evento storage para sincronizar abas, se aplicável.
- Não salvar segredos sensíveis.
- Não expor dados desnecessários.

Cenário B — Sistema usa API/backend:
- Validar respostas.
- Tratar HTTP errors.
- Tratar timeout/rede.
- Atualizar estado após mutações.
- Não confiar apenas em estado otimista sem rollback.
- Garantir idempotência quando possível.
- Garantir autorização no backend.

Cenário C — Sistema híbrido:
- Definir fonte primária de verdade.
- Evitar duplicação.
- Normalizar dados antes de exibir/usar.
- Registrar origem das mutações.

Regra crítica:
Index e Panel devem operar sobre a mesma fonte lógica. Se hoje não operam, criar adapter/serviço comum sem alterar UI.

19. RISCOS CONHECIDOS E MITIGAÇÕES
============================================================

Risco 1 — Alterar sem querer CSS/classe visual
Mitigação: não renomear classes; não alterar estilos; validar seletores.

Risco 2 — Quebrar armazenamento existente
Mitigação: migração defensiva; backup lógico; parse seguro.

Risco 3 — Divergência entre Index e Panel
Mitigação: fonte única de verdade; evento de sincronização; refresh pós-mutação.

Risco 4 — Concorrência entre abas
Mitigação: validação final antes de salvar; version/timestamp; tratamento de conflito.

Risco 5 — Criar UI nova acidentalmente
Mitigação: usar apenas containers existentes; bloquear criação de novos componentes.

Risco 6 — Inventar módulo futuro como Firebase/Supabase
Mitigação: não implementar agora; apenas preparar contrato lógico se necessário.

Risco 7 — Quebrar acesso demo Admin/Admin
Mitigação: preservar fluxo existente; validar perfil após login.

Risco 8 — Exposição indevida de dados
Mitigação: permissões por perfil; escopo por paciente; logs sem dados sensíveis.
